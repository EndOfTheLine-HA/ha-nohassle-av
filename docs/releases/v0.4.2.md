# v0.4.2: route changes no longer make the matrix unavailable

Changing an input from Home Assistant switched the matrix, but every selector and
the Power sensor then showed **unavailable** for about 15 seconds. A second
selector change made in that time reported success and did nothing, because Home
Assistant skips commands sent to unavailable entities.

## Cause

For up to about a second after it accepts a command, the matrix refuses new
connections. Measured on the tested unit on 2026-11-06. The status request sent
right after a route change was refused, and so was its immediate retry. Windows
retries a refused connection by itself, which hid this in tests run from a Windows
PC. The 0.3.1 fix covered a different failure: connections the matrix had already
closed.

## Changes

- A refused connection is retried after short pauses, for up to 1.5 seconds in
  total. A refused connection never carried the request, so a command cannot be
  sent twice. Other connection errors keep the single retry, so an unreachable
  matrix still shows as unavailable promptly.
- For 5 seconds after an accepted routing command, a status read that still fails
  keeps the last routes instead of making the selectors unavailable. This works
  like the 60-second window after power commands and never shortens it.
- The README and AUDIT describe the refusal. They also cover that opening the
  matrix's own web page makes it send a routing report once, which Home Assistant
  can miss if the page reads it first, and that ping was lost for about 11 seconds
  during one power on.

Tested on the same unit: single routes, two route commands sent with no gap, and
Outputs: All all updated within about a second, with no entity going unavailable.

## Upgrading

Update No Hassle AV in HACS and restart Home Assistant. No configuration changes.
